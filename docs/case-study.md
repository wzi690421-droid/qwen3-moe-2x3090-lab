# 从双 RTX 3090 部署走到 MoE 算子优化

实验日期：2026-10-03。飞书导入版整理日期：2026-10-04。

这次实验最初想解决一个问题：用能负担的双 RTX 3090，部署官方 Qwen3 MoE 权重，找出实际性能瓶颈，并逐步形成可以验证的框架优化。

目前做到：服务已运行，TP、EP、eager 已有对照，热点已对应到代码，并有一个只占用单张 GPU 的 Marlin 测量脚本。候选优化还没有运行，也没有证实的新性能收益或已提交 PR。

## 沿着工程问题读懂这次实验

### 1 先确定这次到底要回答什么

模型成功回答问题，只能说明部署链路基本可用。要继续优化，我们还需要知道：相同负载下多快，哪部分耗时，准备改变哪段实现，以及改完怎样验证。

这次的推进顺序可以读成五个问题：

1. **能运行吗**：权重、运行时、两卡通信是否可用，API 是否正常返回。
2. **基线是多少**：固定模型、版本、请求和调度参数后，记录吞吐与延迟。
3. **改变专家分布有没有帮助**：保持 attention TP=2，把专家从 TP 分片换成 EP 分布。
4. **时间花在哪里**：把 GPU 时间拆成 prefill、decode，再看计算与通信。
5. **能否缩小实验**：从完整模型中提取一个热点算子，先在单卡上测试候选。

前三步建立对照，后两步开始定位可以改代码的地方。当前停在第五步的默认配置测量，候选优化还没有闭环。

### 2 读数据前先认识六个词

| 名称 | 在这次实验里是什么意思 |
|---|---|
| prefill | 处理输入 prompt，建立后续生成需要的 KV cache |
| decode | 根据已有上下文，逐步生成新 token |
| TTFT | 从请求开始到首个输出 token 的时间，包含排队等影响 |
| TPOT | 请求内平均每个后续输出 token 的时间；越小越快 |
| 输出吞吐 | 测试总输出 token 除以测试时长，表示这组负载下的总处理能力 |
| kernel | GPU 上执行的一段计算；profiler 中可观察其名称和耗时 |

要分清“服务处理多少请求”与“GPU 一段代码执行多久”。服务指标帮助评价体验和容量，kernel 指标帮助找代码热点；两者的计时边界不同。

### 3 为什么打开 EP 没有变得更快

先看权重分布。每个 MoE 层有 128 个专家，每个 token 选择 8 个。TP=2 时，每张卡都有所有专家的矩阵分片；EP=2 时，每张卡拥有 64 个完整专家。专家分布变了，计算形状也跟着变了。

本轮固定 1024 输入、256 输出、并发 8 的结果是：

| 配置 | 输出吞吐 | 首 token 时间 | 后续 token 时间 |
|---|---:|---:|---:|
| TP 默认编译与 graph | 392.36 tok/s | 1201.07 ms | 15.73 ms |
| EP 默认编译与 graph | 366.46 tok/s | 818.68 ms | 18.42 ms |

表中的延迟是两轮各自 P50 的均值。EP 总吞吐低约 6.6%，首 token 更早，后续生成更慢。评价配置时必须同时看指标和实际需求。

目前可以说：在这组机器和负载下，以总吞吐为目标，TP 更适合作为后续优化起点。不能据此把 EP 判定成普遍无效。我们只测试了一个模型、一个版本和一台双 3090；同一配置下两轮重复也不是充分的统计检验。

更关键的证据来自代码和 trace：本轮 EP 仍有每个 forward 97 次 AllReduce。开关改变了专家权重分布，没有减少这里观测到的归并次数。理解 EP 的效果，需要核对实际执行的通信和 kernel。

### 4 为什么不能直接沿着通信占比 64% 去优化

最初把整个 trace 放在一起看，TP 与 EP 的 NCCL AllReduce 分别占 GPU busy 时间约 63.44% 和 64.44%。这个结果包含输入处理、混合步骤和生成，且 profiler 会带来开销。

我们的目标包括提升生成速度，所以还要单独看纯 decode。在 GPU 执行区间中，选出 batch=8 的 26 个完整 decode step 后，得到：

| 纯 decode 的热点 | TP 中的占比 | EP 中的占比 |
|---|---:|---:|
| MoE Marlin 计算 | 40.19% | 40.33% |
| NCCL AllReduce | 25.64% | 25.70% |

这里的分母是所选区间内 kernel duration 总和，前面的 64% 则使用 GPU busy 时间区间并集。第二部分保留两套口径，方便复核。

分阶段之后，MoE 计算成为生成阶段最大的单项分组。我们因此把下一步问题缩小为：**小 batch 下，Marlin 的专家 GEMM 有没有可以改进的调度选择。** 这是一条值得验证的假设，目前还没有性能收益数据。

这也是一个重要的工程习惯：先固定自己想改善的阶段，再用这个阶段的测量决定下一条实验。

### 5 W13 是什么 为什么只测它

一个专家可以按下面的计算过程理解：

```text
输入隐藏向量 x
  → gate 投影和 up 投影
  → SiLU(gate) × up
  → down 投影
  → 按 router 权重参与最终输出
```

实现把 gate 和 up 两次投影放在同一个 GEMM 中，通常称为 W13；down 是 W2。本轮探针只测 W13。

输入隐藏维度是 2048，完整专家中间维度是 768。TP=2 把中间维度分成每卡 384；合并 gate 与 up 后，单卡 W13 输出维度是 384×2=768。

因此探针里的形状是：

| 参数 | 数值 | 具体含义 |
|---|---:|---|
| M | 8 | 本次输入有 8 行 token 隐藏向量 |
| K | 2048 | 每行输入的隐藏维度 |
| N | 768 | 当前 TP 分片的 gate 与 up 合并输出维度 |
| E | 128 | 专家总数 |
| top-k | 8 | 每行选择 8 个专家 |

从完整服务拆到这个探针后，不需要启动两卡推理服务，也不需要把 NCCL 混进计时。我们可以先问一个具体问题：固定权重、输入和路由，换一个 launch 配置会不会更快，输出误差是否仍可接受。

### 6 用这次路由理解 padding

8 行输入，每行选择 8 个专家，共产生 64 条 token-expert 路由。这次 seed=7 的路由触及 45 个专家，很多专家只拿到很少的行。

当前 kernel 按每专家至少 8 行对齐，于是 45 个专家对应 360 条 padded 行。有效路由行比例为 64/360，约 17.8%。

这解释了为什么小 batch 的专家计算值得观察：每个专家的有效工作很少，仍需要满足 kernel 的形状和调度要求。17.8% 是逻辑行的比例，不能直接当作 GPU 利用率，也不能据此宣称剩下的 82.2% 都可以省掉。

### 7 88 微秒证明了什么

默认配置五轮计时的中位数为 88.05 μs；相对 FP32 反量化参照的 L2 误差约 0.228%；同配置 replay 的输出最大差为 0。

这说明当前固定 fixture 有一个数值检查通过、短期重复稳定的默认测量，可以供候选对比。它使用官方第 0 层权重，但输入和路由是合成的；计时也没有包含权重加载、路由生成、排序或通信。

候选优化、完整专家、整模型质量和真实路由分布尚未验证。这个测量最有用的地方，是给下次实验提供明确起点，而不是提前给出加速结论。

### 8 下次怎样把研究变成一次有证据的改动

下一步先读默认 launch selector，再提出一个具体候选。例如，某个 tile 或 blocks-per-SM 选择是否更适合 M 很小的形状。先写下预测，再测。

验证分三个层次：

1. **单算子**：相同权重、输入和路由做默认 A → 候选 B → 默认 A；重复计时并检查数值。
2. **扩大形状与数据**：覆盖多个 M、seed、路由分布和 W2，判断收益范围和回退。
3. **完整服务**：确认实际模型执行到了新路径，再测固定负载的任务表现、延迟、吞吐和错误率。

前一个层次通过后，再进入下一个层次。若候选单算子无稳定收益，结束该候选就能节省整机测试时间。若单算子更快，也还需要确认它能改善完整服务。

要成为上游性能 PR，还要在拟贡献的 commit 上复验、检查已有实现与讨论，并给维护者说明适用硬件、形状、收益和可能回退。目前这些工作尚未完成。

### 9 用这份材料学工程时怎么练

建议先做到三个能独立解释的点：

- 给出 TP 与 EP 的矩阵形状，说明为什么本轮 W13 的 N=768。
- 从原始 JSON 找到一条性能结果，说明输入、输出、并发、计时口径与重复次数。
- 沿着 Python 封装找到 native 算子的入口，说明计时包含哪些步骤、候选准备改变哪个因素。

然后自己写一个小维度 CPU MoE，逐步验证 router、top-k、专家计算和 combine。代码链路笔记提供实际代码的阅读入口。能说明“我为什么跑这条实验、证据支持什么、下一步会怎样证伪”，这份实验才会转化为自己的工程能力。
